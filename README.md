# mini-mmo-server

넓은 2D 맵에 다수 사용자가 접속했을 때 **각자에게 필요한 정보만 골라 보내
브로드캐스트 비용을 줄이는 것**을 다룬 게임 서버입니다.

게임을 만드는 프로젝트가 아니라, **게임 서버가 겪는 문제 하나를 골라 재현하고 측정한**
프로젝트입니다. C++는 이번이 처음이고, C로 소켓·pthread 기반 게임 서버를 만든 경험을
바탕으로 온라인 게임 서버에서 실제로 문제가 되는 지점을 골랐습니다.

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
./build/mmo-server --mode grid --map 3500 --tick 20
./build/mmo-bot --count 200 --map 3500 --pattern uniform --duration 30
```

---

## 문제

서버가 들고 있는 상태는 O(N)입니다. 200명의 좌표는 다 합쳐도 몇 KB입니다.
무너지는 쪽은 **배포**입니다.

```
각 entity의 상태를 나머지 전원에게  →  tick당 전송량 = N × (N-1) × 상태크기
```

같은 데이터를 수신자 수만큼 복제해 내보내야 하기 때문입니다. 단일 프로세스라면 참조
하나로 공유해서 공짜지만, 연결이 갈리면 각 소켓으로 따로 써야 합니다.

**AOI(Area of Interest)** 는 "이 사람에게 지금 의미 있는 범위"만 보내 `N × K`로 바꾸는
기법입니다. K가 N과 무관한 상수로 유지되면 O(N)이 됩니다.

## 세 단계로 나눠 측정했습니다

| 모드 | broad phase | narrow phase | 무엇을 보는가 |
|---|---|---|---|
| `broadcast` | 전원 | 없음 | 기준선. 필터 없이 전원에게 |
| `naive` | 전원 | 있음 | **전송량**을 무엇이 줄이는가 |
| `grid` | AOI가 걸치는 셀만 | 있음 | 그 판정을 **얼마나 싸게** 하는가 |

처음에는 `naive`와 `grid` 둘만 두었는데, 전송 바이트가 거의 같게 나왔습니다.
`naive`에도 narrow phase가 있어 이미 화면 밖은 보내지 않고 있었기 때문입니다.
**전송량을 줄이는 것은 AOI 개념 자체이고, 공간 분할이 줄이는 것은 판정에 이르기까지의
후보 수라는 것**이 그때 분리됐고, 기준선 모드를 추가해 둘을 나눠 측정했습니다.

## 결과

부하 계단, 밀도 고정(맵 한 변을 √N에 비례), uniform, 20Hz, Release.

| N | `broadcast` bytes/s | `naive`·`grid` bytes/s | `naive` 후보 | `grid` 후보 |
|---:|---:|---:|---:|---:|
| 50 | 406,443 | 85,385 | 48.4 | **19.8** |
| 100 | 1,651,423 | 240,520 | 96.9 | **26.1** |
| 200 | 6,392,045 | 493,868 | 192.2 | **29.8** |
| 400 | 24,815,781 | 941,731 | 380.1 | **29.3** |

- **N이 8배일 때 `broadcast`는 61배, AOI 적용본은 11배.** O(N²)와 O(N)
- **`grid`의 broad phase 후보 수는 N과 무관하게 29~30으로 유지됩니다.** `naive`는 380까지 늘어납니다
- `grid`의 precision 0.47은 기하 계산 예측치와 맞습니다 — AOI 면적 1000² 대비 3×3 블록 1500² = 44.4%

### 한계도 측정했습니다

| 패턴 | K | `grid` 후보 | cell transitions |
|---|---:|---:|---:|
| uniform | 14.07 | 29.8 | 4,632 |
| **hotspot** | **47.33** | 70.0 | 3,902 |
| **border** | 22.09 | 36.7 | **43,942** |

- **hotspot** — 60%를 좁은 구역에 가두면 K가 3.4배로 뜁니다. AOI는 entity가 흩어져 있다는
  가정 위의 최적화라, 그 가정이 깨지면 효과가 사라집니다. 실제 게임이 채널·인스턴스로
  한 공간의 인원에 상한을 두는 이유입니다
- **border** — 셀 경계에서 진동시키면 cell transition이 11배로 뜁니다. 격자 AOI 고유의 약점입니다

전체 수치와 조건은 [`docs/BENCH.md`](docs/BENCH.md)에 있습니다.

## 구조

```
   [클라이언트 N개]
         │ TCP
   ┌──────────────┐  명령 큐  ┌─────────────────────┐  송신 큐  ┌──────────────┐
   │  수신 스레드  │ ────────▶ │  tick 스레드 (1개)  │ ────────▶ │  송신 스레드  │
   │  (연결당 1)  │           │  게임 상태 전담      │           │  (연결당 1)  │
   └──────────────┘           └─────────────────────┘           └──────────────┘
```

**게임 상태는 tick 스레드만 만집니다.** 스레드 경계가 큐 두 개뿐이라 World와 grid에
락이 필요 없습니다.

**tick이 직접 `send`를 부르지 않습니다.** 느린 클라이언트 하나가 `send`에서 막히면 tick
전체가 밀려 게임 시간이 네트워크 사정에 묶입니다. 송신 큐가 넘치면 오래된 스냅샷부터
버립니다 — 스냅샷이 전체 상태라 이전 것 없이 해석되기 때문에 가능한 정책입니다.

**entity 슬롯은 시작할 때 고정합니다.** 실행 중 `vector`가 재할당되면 tick이 순회하는
도중에 무너집니다. id를 곧 슬롯 인덱스로 쓰기 때문에 grid가 id를 담아도 dangling이
생기지 않습니다.

설계 판단과 기각한 대안은 [`docs/decisions/`](docs/decisions/)에 있습니다.

## 이 프로젝트가 하지 않는 것

그래픽 클라이언트 · epoll/IOCP 이벤트 루프 · DB 영속화 · 인증 · 몬스터와 전투 ·
델타 전송 · 아이템 거래 등 상태 변경 트랜잭션

I/O는 **클라이언트당 스레드(blocking)** 입니다. 이벤트 루프를 쓰지 않은 이유는
측정하려는 값이 tick당 브로드캐스트 대상 수이고, 그것이 I/O 다중화 방식과 독립이기
때문입니다. 기간이 짧았던 것도 사실입니다.

**측정 결과 이 규모에서는 스레드 모델이 병목이 아니었습니다.** 400봇에서도 tick 예산의
4.5%만 쓰고 overrun은 0회였습니다. 한계 지점은 더 큰 규모에 있고, 이 측정만으로
"이벤트 루프가 필요하다"고 말할 근거는 없습니다.

## 다음 단계

- **Interest list** — enter/leave 이벤트만 보내는 델타 전송. 지금은 매 tick 전체 상태를 보냅니다
- **Entity cap** — 가까운 M명만 보내 hotspot에서도 K의 상한을 보장
- **채널·인스턴스** — 한 공간의 인원에 상한을 두어 K를 구조적으로 제한
- **이벤트 루프** — 스레드 모델의 한계 지점을 실측한 뒤에

## 착안점

메이플스토리의 채널·필드 구조에서 착안했으나 좌표계는 top-down 2D로 단순화했습니다.
원작의 사이드뷰 플랫폼 물리는 공간 분할 검증과 무관해 제외했고, 에셋과 상표는
사용하지 않았습니다.
