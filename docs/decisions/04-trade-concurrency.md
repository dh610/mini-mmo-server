# 아이템 거래와 동시성 — 구현하지 않음

## 상태

**구현하지 않았다.** 제출 기한 안에 AOI 측정을 끝내는 쪽을 택했다.

## 원래 계획

거래를 tick 밖에서 병렬 처리하고 락으로 정합성을 지키려 했다. 3단계로 나눠
락 없는 버전에서 아이템 복사를 재현하고, 락을 걸었을 때 순서를 안 맞춰 생기는
데드락을 재현한 뒤, `std::scoped_lock`으로 순서를 고정해 해결하는 순서였다.
검증은 ThreadSanitizer로 할 계획이었다.

tick 스레드로 직렬화하면 락 없이도 원자성이 보장되고 데드락이 불가능하다.
실무 게임 서버에서 흔한 선택이다. 그럼에도 병렬을 택하려 한 이유는, 실제
서비스에서 거래에는 검증·영속화·로그가 붙고 그걸 tick 스레드에서 처리하면
게임 루프가 밀리기 때문이다. tick이 `send`를 직접 부르지 않는 것과 같은 원리다.

## 현재 서버의 동시성 구조

거래가 없으므로 **게임 상태를 만지는 스레드는 tick 하나뿐**이다. 수신 스레드는
명령 큐에만 넣고, 송신 스레드는 큐에서 꺼내 보내기만 한다. 스레드 경계가 큐 두
개로 좁혀져 있어 World와 grid에는 락이 없다.

동시 접근이 있는 곳은 셋뿐이다.

- 명령 큐 (`cmdMutex_`) — tick이 통째로 swap해 가져가고 락을 즉시 놓는다
- 슬롯 free list (`slotMutex_`) — 수신 스레드들끼리의 경쟁만 보호한다
- 송신 큐 (`SendQueue`) — mutex + condition_variable
