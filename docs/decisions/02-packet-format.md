# 패킷 형식 — 고정 헤더 + 필드별 직렬화

## 무엇을 정했나

```
[ length(2B) ][ type(2B) ][ sequence(4B) ][ payload ... ]
```

모든 필드를 상위 바이트부터 하나씩 써서 직렬화한다. 구조체를 `memcpy`로 통째 보내지 않는다.
정의는 `src/net/Packet.h` 하나에 모으고 서버와 봇이 같은 파일을 쓴다.

## 왜

**결정적인 이유는 Snapshot이 가변 길이라는 것이다.** 주변에 몇 명이 있는지가 tick마다
달라서, 구조체 하나로 표현할 수가 없다. `std::vector`를 `memcpy`하면 힙 포인터 값이
전송된다.

부차적인 이유:

- **패딩** — 값이 9바이트인 구조체가 12바이트로 나간다. 그 3바이트는 초기화되지 않은
  메모리다. 낭비이자 정보 유출 경로다
- **정렬** — 수신 버퍼에서 패킷은 임의 오프셋에서 시작한다. 그 주소를 구조체 포인터로
  캐스팅해 읽는 것은 정의되지 않은 동작이다. `memcpy` 역직렬화는 이 문제가 없다
- **엔디안** — 구조체 전송은 네이티브 순서로 나간다. 고른 것이 아니라 물려받은 것이다
- **필드 추가** — `sizeof`가 바뀌어 서버와 클라이언트를 동시에 다시 빌드해야 한다

`length`는 헤더를 포함한 전체 길이다. TCP는 바이트 스트림이라 패킷 경계를 알려주지 않고,
길이를 모르면 어디서 잘라야 할지 알 수 없다.

`sequence`는 순서 보장용이 아니다. TCP가 이미 순서를 지킨다. **서버가 보낸 수와 봇이 받은
수를 대조해 측정을 검증하고, 송신 큐에서 버려진 스냅샷을 추적하기 위한 것**이다.
실제로 모든 측정에서 `snapshot_gaps` 0을 확인했다.

## 검토했으나 쓰지 않은 것

**구조체 통째 전송** — 위 이유로 가변 길이를 표현할 수 없다. 고정 크기 패킷만 있었다면
`#pragma pack(1)`과 명시적 엔디안 변환으로 쓸 수 있었겠지만, 핵심 패킷이 가변 길이다.

**패킷 길이를 4의 배수로 맞추기** — 수신 버퍼에서 바로 캐스팅할 수 있게 되지만, 이 불변식은
사람이 지켜야 유지된다. 새 패킷을 추가하면서 어기면 컴파일도 테스트도 통과한 채 특정
조건에서만 터진다. `memcpy` 역직렬화는 정렬을 요구하지 않아 이 규약 자체가 필요 없다.
