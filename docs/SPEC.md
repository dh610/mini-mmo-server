# 명세

## 시나리오

메이플스토리 한 채널의 넓은 사냥 지역. 플레이어들이 2D 평면을 돌아다니고,
서로가 화면에 보이고, 근처 사람과 대화하고, 아이템을 주고받는다.

**메이플 에셋·IP는 사용하지 않는다.** 착안점만 README에 밝힌다.

| 항목 | 값 | 근거 |
|---|---|---|
| 좌표계 | top-down 2D | grid AOI에 자연스러움. 원작의 사이드뷰 플랫폼 물리는 검증 대상과 무관해 제외 |
| Entity | 플레이어만 | 몬스터는 AOI 측정에 기여 없음 |
| 행동 | 이동 / 채팅 / 아이템 거래 | 앞 둘은 AOI, 마지막은 동시성 |

## 파라미터

| 이름 | 값 | 실행 인자 | 근거 |
|---|---|---|---|
| AOI 모양 | **정사각형** | — | 카메라 고정 2D라 가시 영역이 직사각형. 셀과 모양이 일치해 precision 44.4% (원이면 34.9%). narrow phase도 곱셈 없이 비교 2번 |
| a (half-extent) | 500 | `--aoi` | 1024×768 화면 절반(512)에서 반올림 |
| cell size | 500 (= a) | `--cell` | 3×3 순회. precision 44.4%, 방문 셀 9 |
| 맵 한 변 | 3500 (7×7 셀) | `--map` | K ≈ 16. **cell size의 정수배로 유지할 것** (가장자리 잘린 셀 방지) |
| 틱레이트 | 20Hz 기본, 30Hz 비교 | `--tick` | 2D MMO 장르 적합. 60Hz는 불필요 |
| 모드 | naive / grid | `--mode` | 같은 빌드로 연속 측정 |

### 밀도 고정 스케일링

부하를 올릴 때 맵도 같이 키워 K를 상수로 유지한다. **이걸 안 하면 AOI를 켜도 제곱으로 늘어
"AOI가 O(N)을 만든다"가 안 보인다.**

| N | grid | 맵 | K |
|---|---|---|---|
| 50 | 4×4 | 2000 | 12.5 |
| 100 | 5×5 | 2500 | 16.0 |
| 200 | 7×7 | 3500 | 16.3 |
| 400 | 10×10 | 5000 | 16.0 |

## 스레드 구조

```
   [클라이언트 N개]
         │ TCP
   ┌──────────────┐  명령 큐  ┌─────────────────────┐  송신 큐  ┌──────────────┐
   │  수신 스레드  │ ────────▶ │  Tick 스레드 (1개)  │ ────────▶ │  송신 스레드  │
   │  (연결당 1)  │           │  게임 상태 전담      │           │  (연결당 1)  │
   └──────────────┘           └─────────────────────┘           └──────────────┘
```

**원칙: 게임 상태는 tick 스레드만 만진다.** 스레드 경계는 큐 두 개뿐이다.
(아이템 거래만 예외 — 아래 참조)

**tick 스레드가 직접 `send`하지 않는 이유**: 느린 클라이언트 하나가 `send`에서 막히면
tick 전체가 밀린다. 사용자가 2023년에 만든 C 게임 서버에서 게임 시간이 송신 스레드의
`sleep(1)`에 묶여 있던 것과 같은 구조적 실수다.

## Tick 절차

```
1. 명령 큐 비우기        → 이동·채팅 요청 적용
2. 이동 적용             → 좌표 갱신, 셀이 바뀌면 grid에서 remove/insert
3. AOI 계산              → broad phase(3×3) → narrow phase(사각형 판정)
4. 스냅샷 조립·직렬화     → 각 클라이언트 송신 큐에 push
5. 지표 수집             → K, candidates, 송신 바이트, tick 소요 시간
6. 남은 시간 대기
```

**naive와 grid는 3단계의 "후보 수집"에서만 갈린다.** narrow phase 이후는 완전히 동일해야
비교가 공정하다. **naive에서도 narrow phase를 돌린다** — 안 그러면 AOI 효과와 필터링 효과가 섞인다.

## 패킷

```
[ length(2B) ][ type(2B) ][ sequence(4B) ][ payload ... ]
```

- 필드별 **명시적 직렬화**. 구조체 통째 전송(`memcpy`) 금지
- 정의는 **공유 헤더 하나**에 모으고 서버·봇이 같은 파일을 쓴다
- **왕복 테스트 필수** (serialize → deserialize → 원본과 동일)
- `sequence`는 순서 보장용이 아니라 **송수신 대조와 드롭 추적용**

## 스냅샷 · 송신 큐

- 스냅샷은 **전체 상태**(AOI 안 모든 entity의 위치). 델타는 next step
- 송신 큐가 상한을 넘으면 **오래된 스냅샷을 버린다**
  - 근거: 스냅샷이 전체 상태라 이전 것 없이 해석 가능하다. 델타였다면 중간을 버릴 수 없다

## 아이템 거래 — 유일한 예외

거래는 tick 밖에서 병렬 처리하고 락으로 정합성을 지킨다.

**근거**: 실제 서비스에서 거래에는 검증·영속화·로그가 붙는다. tick 스레드에서 처리하면
게임 루프가 밀린다. (tick이 `send`를 직접 안 하는 것과 같은 원리)

**3단계로 구현한다. 2단계를 건너뛰지 말 것.**

```
1. naive     — 락 없이 두 인벤토리 수정 → 아이템 복사 재현 → TSan 검출
2. 락 추가   — 순서를 안 맞춰서 데드락 발생 → 재현
3. 순서 고정 — std::scoped_lock → 해결, TSan 통과
```

## 측정

| 지표 | 성격 |
|---|---|
| **초당 송신 바이트** | **주 지표** |
| K (tick당 평균 수신자) | AOI가 실제로 몇 명으로 좁혔나 |
| candidates | broad phase가 넘긴 후보 수 |
| precision = K / candidates | broad phase 정확도 |
| tick overrun 횟수 | 예산 초과. I/O 모델의 한계 지점 |

**주 지표가 패킷 수가 아닌 이유**: 배칭하면 클라이언트당 tick마다 1패킷이라
AOI를 켜도 패킷 **수**는 안 줄고 **크기**가 준다.

**측정 조건을 항상 함께 기록한다** — 머신, N, 지속 시간, **시드**, 맵, a, cell, 틱레이트,
빌드 타입, 커밋 해시. 조건 없는 숫자는 나중에 방어할 수 없다.

## 봇 분포 (`--pattern`)

| 값 | 목적 |
|---|---|
| `uniform` | 기준. AOI가 잘 동작하는 조건 |
| `hotspot` | 밀집. **AOI가 무력해지는 것을 확인** |
| `border` | 셀 경계 진동. **격자 AOI 고유의 약점** |
| `idle` | 접속만, 이동 없음. **원인 분리용 대조군** (컨텍스트 스위칭 vs 브로드캐스트 처리량) |

**부하 단계**: 50 → 100 → 200 → 400 계단식. 봇 접속은 10~20ms 간격 램프업
(`kern.ipc.somaxconn`이 128이라 동시 접속하면 일부가 거절된다).
