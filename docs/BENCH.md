# 벤치마크

## 측정 환경

| 항목 | 값 |
|---|---|
| 머신 | Apple M5, 10코어 (성능 4 / 효율 6), macOS 15 |
| 컴파일러 | Apple clang 21, C++17 |
| 빌드 | Release (`-O3`), 샌디타이저 없음 |
| 커밋 | `83f60f9` |
| 시드 | 42 (봇마다 `seed + index`) |
| 틱레이트 | 20Hz (틱 예산 50,000μs) |
| AOI | 정사각형, half-extent 500 |
| cell size | 500 |
| 봇 램프업 | 6~8ms 간격 |

봇과 서버가 같은 머신에서 돈다. 그래서 CPU 사용률과 지연은 봇이 코어를 먹어 오염되지만,
**초당 송신 바이트와 candidates는 서버가 자기 로직으로 세는 값이라 그 오염과 무관하다.**

## 세 가지 모드

| 모드 | broad phase | narrow phase |
|---|---|---|
| `broadcast` | 활성 entity 전부 | **없음 — 전원에게 보낸다** |
| `naive` | 활성 entity 전부 | 있음 |
| `grid` | AOI가 걸치는 셀만 | 있음 |

`naive`와 `grid`는 narrow phase가 동일하다. 판정이 다르면 비교가 성립하지 않는다.
그래서 두 모드의 K는 항상 같아야 하고, 실제로 소수점까지 일치한다 — 이것이 두 경로가
같은 결과를 낸다는 검증이기도 하다.

## 재현

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
COUNT=200 MAP=3500 DURATION=10 ./scripts/bench.sh
```

## 1. 부하 계단 — 밀도 고정

맵 한 변을 √N에 비례시켜 K를 상수로 유지했다. **이걸 안 하면 부하를 올릴 때 밀도가 같이
올라 K가 커지고, AOI를 켜도 전송량이 제곱으로 늘어 O(N) 특성이 측정에 나타나지 않는다.**

패턴 uniform, 10초.

| N | 맵 | `broadcast` bytes/s | `naive`·`grid` bytes/s | K |
|---:|---:|---:|---:|---:|
| 50 | 2000 | 406,443 | 85,385 | 9.50 |
| 100 | 2500 | 1,651,423 | 240,520 | 13.39 |
| 200 | 3500 | 6,392,045 | 493,868 | 14.07 |
| 400 | 5000 | 24,815,781 | 941,731 | 13.62 |

**N이 8배(50→400)일 때 `broadcast`는 61배, AOI 적용본은 11배.**
전자는 O(N²)(8²=64), 후자는 O(N)에 해당한다.

### broad phase 후보 수

| N | `naive` candidates | `grid` candidates | `grid` precision |
|---:|---:|---:|---:|
| 50 | 48.4 | **19.8** | 0.481 |
| 100 | 96.9 | **26.1** | 0.513 |
| 200 | 192.2 | **29.8** | 0.473 |
| 400 | 380.1 | **29.3** | 0.466 |

**`naive`의 후보 수는 N에 비례해 늘고, `grid`는 상수로 유지된다.** 공간 분할이 하는 일이
정확히 이것이다. precision 0.47은 기하 계산 예측치와 맞는다 —
AOI 면적 1000² 대비 3×3 블록 면적 1500²이 44.4%.

**전송 바이트는 `naive`와 `grid`가 같다.** `naive`에도 narrow phase가 있어 이미 화면 밖은
보내지 않기 때문이다. 즉 전송량을 줄이는 것은 AOI 개념(narrow phase)이고,
공간 분할이 줄이는 것은 그 판정을 하기까지의 후보 수, 곧 CPU 작업량이다.

## 2. 이동 분포별 (N=200, 맵 3500, 10초)

| 패턴 | K | `naive` cand | `grid` cand | `grid` precision | bytes/s | cell transitions |
|---|---:|---:|---:|---:|---:|---:|
| uniform | 14.07 | 192.2 | 29.8 | 0.473 | 493,721 | 4,632 |
| **hotspot** | **47.33** | 192.2 | **70.0** | 0.676 | **1,594,900** | 3,902 |
| **border** | 22.09 | 192.1 | 36.7 | 0.602 | 758,997 | **43,942** |
| idle | 13.14 | 184.1 | 27.6 | — | 375,746 | 195 |

### hotspot — AOI의 한계

60%를 맵 중앙 좁은 구역에 가뒀다. **K가 14.07에서 47.33으로 3.4배, 전송량이 3.2배 늘었다.**

AOI는 "entity가 공간적으로 흩어져 있다"는 가정 위에 서 있는 최적화다. 그 가정이 깨지면
효과가 줄고, 극단적으로 전원이 한 셀에 모이면 `broadcast`와 같아진다.
precision이 0.473에서 0.676으로 오른 것도 같은 현상이다 — 후보 대부분이 실제로 시야 안에 있다.

**알고리즘으로 풀리지 않는 영역이다.** 실제 게임은 채널·인스턴스로 한 공간의 인원에
상한을 두거나, AOI 안 인원을 가까운 M명으로 자르는 방식(entity cap)으로 K의 상한을 강제한다.

### border — 격자 AOI 고유의 약점

봇들이 셀 경계를 사이에 두고 매 tick 진동하게 했다.
**cell transition이 4,632에서 43,942로 11배 늘었다.** 셀을 옮길 때마다 제거·삽입이
따라붙는 bookkeeping 비용이다.

cell size를 줄이면 precision은 오르지만 이 비용도 함께 오른다. cell size = AOI half-extent가
표준인 이유가 이 균형이다.

### idle — 원인 분리용 대조군

접속만 하고 움직이지 않는다. cell transition이 195(초기 스폰분)로 떨어지고,
`grid`의 tick busy가 931.9μs에서 720.3μs로 줄었다. 이동이 없으면 grid 갱신 비용도 없다.

## 3. tick 예산

| N | `broadcast` | `naive` | `grid` | 예산 대비 (`grid`) |
|---:|---:|---:|---:|---:|
| 50 | 242.5μs | 235.9μs | 176.9μs | 0.4% |
| 100 | 469.4μs | 458.5μs | 477.8μs | 1.0% |
| 200 | 1,780.2μs | 932.9μs | 1,198.4μs | 2.4% |
| 400 | 4,794.8μs | 2,486.3μs | 2,239.1μs | 4.5% |

**모든 조건에서 tick overrun 0회.** 20Hz 예산 50,000μs 대비 400봇에서도 4.5%다.

**이 규모에서는 클라이언트당 스레드 모델이 병목이 아니었다.** 스레드 400개가 코어 10개
위에서 도는데도 틱이 밀리지 않았다. 한계 지점은 더 큰 규모에 있고, 이 측정만으로는
"이벤트 루프가 필요하다"고 말할 근거가 없다.

`grid`의 tick busy가 `naive`보다 항상 낮지는 않다(N=100, 200). 후보 수는 6배 이상 줄었지만
셀 순회와 bookkeeping이 그만큼 붙기 때문이고, 현재 규모에서는 두 비용이 비슷한 크기다.
**후보 수 감소가 tick 시간 감소로 이어지려면 narrow phase 자체가 병목이 될 만큼 부하가
커져야 한다.** 이 측정에서는 그 지점까지 가지 않았다.

## 4. 계측의 자기 검증

- **서버의 `K_avg`와 봇의 `visible_avg`가 일치한다** (예: 14.07 / 14.07). 서버가 보냈다고
  센 값과 봇이 실제로 받아 해석한 값이 맞아떨어진다
- **`snapshot_gaps` 0** — 봇이 받은 sequence에 구멍이 없다. 서버 송신 큐에서 버려진
  스냅샷이 없다는 뜻이고, 따라서 전송량 수치가 실제 전달량이다
- **`naive`와 `grid`의 K가 소수점까지 동일** — 후보를 좁히는 방식이 결과를 바꾸지 않았다

## 5. 이 측정이 말하지 않는 것

- 봇과 서버가 같은 머신에서 돌았다. 실제 네트워크 지연·손실은 반영되지 않는다
- 클라이언트가 그래픽을 그리지 않으므로 실제 게임의 클라이언트 부하는 빠져 있다
- 400봇이 상한이었다. 스레드 모델의 한계 지점은 확인하지 못했다
- 스냅샷은 전체 상태다. 델타 전송이었다면 전송량 수치가 전혀 달라진다
