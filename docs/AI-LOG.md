1. **설명하지 못하는 줄은 머지하지 않는다**
2. **AI 제안 중 기각한 것은 이유와 함께 남긴다**
3. **성능 주장은 측정 없이 쓰지 않는다**

주어를 "AI가"로 쓰지 않는다. **판단 내용이 주어**다. 누가 먼저 말했는지는 중요하지 않고,
무엇을 왜 그렇게 정했는지가 기록의 목적이다.

```
### <판단 대상> — 채택 / 기각
무엇이 제안됐고, 무엇을 근거로 어떻게 정했는지. 3~5줄.
```

# 설계 단계 (코드 작성 전)

## AOI 형태를 원에서 정사각형으로 — 채택

view radius를 원으로 잡는 안을 받았으나, 대상 게임은 카메라가 고정된 2D라 실제 가시
영역이 직사각형이다. 사각형으로 바꾸니 broad phase의 셀과 모양이 일치해 precision이
34.9% → 44.4%로 오르고, narrow phase도 곱셈 없이 비교 두 번으로 끝난다.
회전 카메라가 있는 게임이면 회전 불변인 원이 맞다.

## 패킷 길이를 4의 배수로 맞추는 불변식 — 기각

수신 버퍼에서 직접 캐스팅할 수 있게 된다는 제안이었다. 그러나 이 불변식은 사람이
지켜야 유지되고, 새 패킷을 추가하는 사람이 어기면 컴파일도 테스트도 통과한 채 특정
조건에서만 터진다. `memcpy` 역직렬화는 정렬을 요구하지 않으므로 규약 자체가 불필요하다.
미미한 복사 비용으로 유지해야 할 규약 하나를 제거하는 쪽을 택했다.

## Docker + epoll 노선 — 기각 (근거는 정정됨)

처음에 "VM의 네트워크 스택 때문에 성능 측정이 오염된다"는 근거를 받았으나, 확인해보니
서버와 봇을 모두 VM 안에서 돌리면 트래픽이 VM 경계를 넘지 않아 오버헤드가 거의 없다.
근거가 틀렸다. **실제 기각 사유는 논블로킹 I/O 학습 비용이고, 그것도 처음 들은
"2~3일"이 아니라 하루 반이다** — 부분 수신·송신 버퍼는 블로킹 모델에서도 어차피 필요하다.
그럼에도 기각한 이유는 SPEC의 I/O 모델 항목 참조.

## 직렬화 선택지에 스키마 기반이 누락됨 — 보완

처음 받은 선택지는 (a) 손직렬화 (b) 구조체 통째 전송 (c) JSON 셋뿐이었다.
팀 규모에서는 정의가 서버·클라이언트에 중복되어 한쪽만 바뀌면 런타임에 조용히 어긋나는데,
그 해법이 (d) 스키마 기반 코드 생성(protobuf 등)이다. 이 프로젝트는 클라이언트가 하나고
같은 저장소에서 같이 빌드되므로, 공유 헤더 단일 정의와 왕복 테스트로 대체했다.

## 밀도 고정 스케일링 — 채택

부하를 올릴 때 맵을 고정하면 밀도가 올라 K가 같이 커지고, 그러면 AOI를 켜도 전송량이
제곱으로 늘어 "AOI가 O(N²)을 O(N)으로 만든다"는 주장이 측정에 나타나지 않는다.
맵 한 변을 √N에 비례시켜 K를 상수로 유지한다. 맵 고정 시나리오는 hotspot 실험이 담당한다.

## Step 2 — 수신 누적 버퍼로 std::deque 대신 std::vector<uint8_t> — 채택

recv 결과를 계속 이어붙이면서 앞에서부터 소비하는 구조라 큐처럼 쓰고 싶었지만,
recv()는 연속된 메모리 주소(`void* buf`)를 요구하는 C API다. std::deque는 내부적으로
청크 단위로 나뉜 메모리라 `.data()`로 연속 포인터를 못 뽑는다. std::vector만 "동적으로
늘어난다"와 "연속 메모리 보장"을 동시에 만족해 선택했다. 앞부분 소비는 deque의
pop_front 대신 오프셋 인덱스 전진 + 필요할 때만 압축(compaction)으로 대체했다.

## Step 2 — recv 결과를 누적 버퍼에 채우는 방식: 임시 버퍼 대신 vector에 직접 recv — 채택

두 방식을 검토했다: (A) 고정 크기 임시 버퍼로 recv한 뒤 누적 vector에 복사해 이어붙이기,
(B) 누적 vector를 resize로 미리 늘려두고 그 안에 바로 recv. (A)가 더 단순하지만 매번
복사가 한 번 더 생긴다. 지금은 헤더 8바이트뿐이지만 나중에 payload(게임 스냅샷)까지
다루면 이 복사가 tick마다 접속자 수만큼 반복되는 경로가 되므로 (B)를 택했다.
대신 old_size를 resize 전에 캡처해야 한다는 제약이 따른다 (resize가 size()를 바꾸므로).

## Step 2 — 패킷 헤더의 length 필드 = 헤더 포함 전체 길이 — 채택

SPEC에 length가 payload만인지 헤더 포함 전체인지 명시가 안 되어 있어 직접 정했다.
헤더 포함 전체 길이로 하면 drainPackets의 "패킷이 다 도착했는지" 판정이
`accumulator에 length바이트 이상 쌓였는가` 하나로 끝나 로직이 단순해진다.
payload만 잴 경우 매번 8(헤더 크기)을 더해야 하는 번거로움이 생긴다. 또한
"length"라는 이름 자체가 협업 시 "이 레코드의 전체 크기"로 직관적으로 읽혀
다른 사람이 봤을 때 오해 소지가 적다.

## Step 2 — 수신 버퍼 growth를 "capacity 가까워질 때만 resize"로 아끼는 최적화 — 기각

recv 누적 버퍼를 매 루프 `resize(old_size + chunk)` → `recv` → `resize(old_size + n)`로
관리하면, 실제로 받은 n바이트보다 훨씬 큰 chunk만큼을 매번 value-initialization(0-채움)
했다가 버리는 낭비가 있지 않냐는 의문에서 시작됐다. capacity에 여유가 있을 때는 resize
자체를 생략하고 원시 포인터로 먼저 recv한 뒤 나중에 크기만 늘리는 방법을 검토했으나,
std::vector::resize()로 크기를 늘리면 새로 포함되는 원소를 항상 value-initialize하므로
recv로 먼저 써둔 데이터를 다시 0으로 덮어써버린다 — "초기화 없이 크기만 늘리기"는
표준 vector 인터페이스에 없다(커스텀 얼로케이터 없이는 불가능). uint8_t 단위 0-채움
비용 자체가 무시할 수준이고, 아직 벤치마크도 없는 시점이라 규칙 3(측정 없이 성능
주장 금지)에도 걸려 기각. Step 5에서 실측 후 병목으로 확인되면 재검토.

## Step 2 — deserializeHeader를 return {...} 중괄호 초기화로 구현 — 채택

idx를 참조로 넘겨 세 번의 readBigEndian 호출에 걸쳐 순서대로 전진시켜야 하는데,
일반 함수 인자 목록(`f(a(), b())`)은 평가 순서가 표준에 의해 보장되지 않는다.
반면 중괄호 초기화 리스트(`return {a(), b(), c()}`)의 원소는 왼쪽에서 오른쪽
순서로 평가되는 것이 표준에 명시돼 있어, idx의 부작용이 안전하게 순서대로 반영된다.
